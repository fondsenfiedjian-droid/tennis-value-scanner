# Исторические архивы Developer Edition

Откройте **Архив и система → Центр исторических архивов**. Выберите CSV или ZIP и нажмите **Импортировать и обработать**. Обработка запускается автоматически после записи оригинала и задания в IndexedDB. Хэш SHA-256 предотвращает создание второй копии тех же байтов. Центр показывает обработанные файлы и записи, предупреждения, ошибки и кандидатов на совпадение.

## Хранение и контроль качества

- Переход с версии 2 на 3 сохраняет оригиналы и регистрирует задания для них при первом запуске. На том же адресе, в том же браузере и профиле повторный импорт не нужен. Другой домен или профиль имеет собственную IndexedDB.
- SHA-256 проверяется по сохранённому оригиналу. ZIP поддерживает обычные несегментированные архивы без шифрования с методами Stored и Deflate. Перед обработкой каждого CSV из ZIP проверяются размер и CRC-32. Лимит оригинала и суммарного размера CSV после распаковки — 100 МиБ каждый. Каждый CSV внутри ZIP должен иметь поддерживаемую схему. Лишние файлы других форматов пропускаются. Для обоих форматов используется UTF-8.
- Конвейер сохраняет производные записи по ключу «архив / CSV / номер записи», исходные признаки результата и предупреждения о качестве. Строки с неверным числом полей сохраняются с пометкой. Без счёта и явных признаков форфейта, отказа, дисквалификации или прерывания исход по счёту остаётся неизвестным.
- Кандидаты определяются по повторному ID матча или совпадению даты, турнира и пары ID игроков в рамках пространства исходного источника. При неизвестном источнике поиск ограничен одним импортом. Выбор источника служит подсказкой, поэтому любое совпадение требует ручной оценки. Можно указать решение по каждой паре отдельно. Старые решения остаются в исходном реестре и переносятся на новую пару, если совпадают ID матчей и номера записей.
- Для пакетной записи используется одна транзакция IndexedDB на 250 записей. Пауза прекращает работу на границе транзакции. После закрытия приложения прерванная работа продолжается при открытии той же Developer Edition. Явная пауза сохраняется до нажатия **Продолжить**. При возобновлении анализатор повторно читает CSV до сохранённой позиции, сохраняя только новые результаты.
- Одновременно выполняется одно задание на адрес сайта. На Android обработка зависит от жизненного цикла вкладки или PWA. Место для оригинала, записей и индексов предоставляет браузер. При нехватке места ошибка отображается в карточке и остаётся доступна команда **Повторить**.
- Производные записи и решения доступны только в локальном историческом хранилище. Допуск к прогнозной модели требует отдельного решения. PR #192 и задача отсутствующих пар игроков отложены.

## Канонический архив Android

Локальный режим центра архивов использует SQLite из Node.js 24. Он переиспользует адаптеры Developer для CSV, ZIP и AcesAPI и читает готовые таблицы SQLite в режиме read-only. Выходную базу храните в домашней папке Termux. Android может ограничивать файловые блокировки SQLite на общей памяти.

После предоставления Termux доступа к общей памяти (`termux-setup-storage`) выполните из репозитория:

```bash
node developer/archive-termux.mjs inspect /sdcard/Download/TennisCleanArchive
node developer/archive-termux.mjs run /sdcard/Download/TennisCleanArchive "$HOME/tennis-canonical.sqlite"
```

`inspect` выводит имена файлов, таблиц и полей без исходных строк. `run` находит подготовленные SQLite рекурсивно и выбирает распознаваемые таблицы из `matches.sqlite`. При отсутствии таких таблиц он ищет `Normalized/matches_candidates.ndjson` и `Normalized/matches_review.ndjson`. Выбор входов и пропущенные таблицы отражаются в отчёте. Итоговый файл можно открыть в центре исторических архивов Developer:

```bash
cp "$HOME/tennis-canonical.sqlite.report.json" /sdcard/Download/
```

Тот же вызов `run` продолжает обработку с последней подтверждённой пачки. SQLite читает строки по индексу `rowid`, CSV и NDJSON повторно просматриваются до контрольной точки. Контрольная точка и наблюдения записываются одной транзакцией на 500 строк. SHA-256 проверяется на каждом запуске. На время импорта закройте программы, которые меняют подготовленные базы. Новые версии входов можно добавлять как новые пути в манифест. Порядок входов записывается в отчёте. Сохраняйте выходную базу для сохранения назначенных идентификаторов.

### Явные связи и входы

Для неизвестной схемы передайте файл сопоставления третьим аргументом команды `run`. Пример с вымышленными именами таблиц и идентификаторами:

```json
{
  "links": [
    {
      "kind": "tournament",
      "source": "sackmann",
      "scope": "ATP",
      "externalId": "2025-123",
      "targetSource": "atp",
      "targetId": "123",
      "evidence": "Подтверждённый турнир: город и издание совпадают"
    }
  ],
  "inputs": [
    {
      "file": "DB/players.sqlite",
      "table": "profiles",
      "kind": "player_profile"
    },
    {
      "file": "DB/matches.sqlite",
      "table": "results",
      "discipline": "singles",
      "columns": { "provider": "dataset", "match_date": "played_on" }
    },
    {
      "file": "DB/supplemental.sqlite",
      "table": "points",
      "kind": "supplement"
    }
  ]
}
```

Связи откалибруйте перед первой загрузкой. Конфликтующую существующую привязку команда отклонит. Известные имена и псевдонимы сохраняются как утверждения о профиле. Автоматическое связывание ID игроков между источниками требует единственного совпадения по нормализованному имени, дате рождения и контуру тура. Равенство имени используется как часть свидетельства. Турнирные ID связываются подтверждённым сопоставлением либо точным совпадением года, тура, названия, города, категории и покрытия издания. Противоречивые даты рождения блокируют дальнейшее автоматическое использование ID поставщика. Имена турниров и метаданные сохраняются по наблюдениям. Провайдерские ID формируют локальные идентичности при отсутствии межбазовой связи, поэтому отчёт отражает достигнутое покрытие, а итоговая база может содержать отдельные записи одной встречи.

Запись учитывает состав обеих сторон, тур, дисциплину, сезон, сетку и раунд. Для автоматической связи дополнительно нужны совместимые дата, слот сетки или уже сопоставленный ID поставщика. Дата начала турнира хранится отдельно. Счёт приводится к постоянному порядку сторон только при известной ориентации. Противоречия результата и неоднозначные привязки остаются в очереди разбора. Текстовые статусы приводятся к известным категориям. Строка со счётом и без надёжного статуса остаётся со статусом неизвестен. Слот сетки должен обозначать одну и ту же позицию в обоих источниках.

Поддерживаются готовые SQLite с обычным `rowid`, NDJSON, CSV существующих схем, AcesAPI JSON, GZIP для CSV/NDJSON и отдельные CSV/JSON-элементы ZIP через поле `member`. Для размеченной таблицы Excel укажите `excelEpoch` со значением `"1900"` или `"1904"` и сопоставьте столбец с датой. Прямой импорт XLS, XLSX, Parquet и произвольного JSON требует адаптера либо использования подготовленной SQLite/NDJSON. Автораспознавание охватывает таблицы матчей. Профили и дополнения задаются манифестом. Дополнение требует однозначной связи по ID поставщика в том же контуре. Данные с собственным несопоставленным ID, автономные исторические рейтинги и пропущенные таблицы требуют дальнейшей привязки.

### Проверка и пересмотр

`report` выводит число записей матчей, дополнительных наблюдений и изолированных строк, полноту полей, конфликты, `quick_check` и нарушения внешних ключей. Пересечения HuggingFaceOdds и OpenTennisData подсчитываются по совпавшим ID поставщика при наличии путей к исходным файлам в обеих выборках. Этот показатель измеряет обнаруженные пересечения. При разных ID или отсутствии исходного пути он не покрывает все дубли.

`fields БАЗА ID [UTC-СРЕЗ]` показывает значения с источниками и координатами строк. Согласованные значения получают подтверждения по источникам. Для спорного поля выводятся альтернативы, а выбранное значение остаётся пустым. Срез требует UTC-время, исключает значения без подтверждённого времени доступности, значения на границе или после неё, а также результат и послематчевые поля. При формировании предматчевой выборки в качестве границы используйте прогнозное время до начала встречи.

`unlink БАЗА КЛЮЧ_НАБЛЮДЕНИЯ ПРИЧИНА` отменяет присоединение наблюдения. Его значения исключаются из активной записи, исходная строка и решение остаются доступны для аудита. Первичное наблюдение сохраняет постоянный ID матча. Разделение первичной записи на две подтверждённые встречи и повторное применение новых связей к уже импортированным строкам пока требуют отдельного пересмотра. Ссылки на исходные строки и проверенные версии файлов позволяют воспроизвести решения без копирования всего архива в выходную базу.
